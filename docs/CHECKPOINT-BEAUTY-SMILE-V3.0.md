## 💡 Lições Aprendidas

### Durante a Criação dos PRDs

**✅ O que funcionou bem:**
1. **Estrutura padronizada:** Manter formato consistente facilitou muito
2. **Exemplos práticos:** User stories e queries SQL ajudam a visualizar
3. **Constraints detalhados:** Pensar em validações desde o início evita problemas
4. **RLS desde o começo:** Segurança por design, não como afterthought
5. **JSONB estratégico:** Flexibilidade para análises IA sem schema rígido
6. **Triggers para auditoria:** Automação reduz erros humanos
7. **Functions SQL:** Lógica de negócio centralizada no banco
8. **Documentação visual:** Diagramas ER ajudam a entender relacionamentos

**⚠️ Desafios encontrados:**
1. **Balancear flexibilidade vs estrutura:** JSONB vs colunas fixas
2. **Normalização:** Quando criar tabela separada vs JSONB
3. **Performance vs segurança:** RLS policies podem ser pesadas
4. **Versionamento:** Como manter histórico sem poluir
5. **Enums vs tabelas:** Quando usar cada abordagem

**📚 Decisões de arquitetura importantes:**
1. **Singleton para configurações:** Garante apenas 1 registro
2. **Soft delete universal:** Nunca perde dados, crucial para auditoria
3. **Imutabilidade de logs:** Compliance LGPD/ISO
4. **Múltiplos avaliadores:** Consenso reduz viés
5. **Biblioteca de perguntas:** Reuso aumenta produtividade
6. **Templates customizáveis:** Branding sem mexer em código
7. **Webhooks testáveis:** Debugging facilitado

**🎯 Melhores práticas estabelecidas:**
1. Sempre ter `created_at`, `updated_at`, `deleted_at`
2. Sempre ter `created_by`, `updated_by` quando aplicável
3. Índices em FK e campos de filtro frequente
4. RLS policies explícitas por role
5. Constraints de validação no banco (não só frontend)
6. Functions para lógica complexa (DRY)
7. Triggers para automações consistentes
8. Views para queries complexas recorrentes
9. JSONB para dados semi-estruturados (análises IA)
10. Enums para valores fixos conhecidos
