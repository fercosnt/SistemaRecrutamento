**Migration 3: `supabase/migrations/20260420000002_unified_auth_role.sql` (per FOUND-03, D-02b):**

Create the Custom Access Token Hook function exactly as specified in RESEARCH.md Pattern 2:
```sql
-- Migration: Custom Access Token Hook for role injection
-- Requirement: FOUND-03
-- Injects role into JWT app_metadata so the client can read it without a DB query.
-- IMPORTANT: After applying this migration, enable the hook in Supabase Dashboard:
-- Authentication -> Hooks -> Custom Access Token -> Enable -> Select: custom_access_token_hook

CREATE OR REPLACE FUNCTION public.custom_access_token_hook(event jsonb)
RETURNS jsonb
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
  claims jsonb;
  user_role text;
BEGIN
  -- Check usuarios_rh first (rh or administrador)
  SELECT
    CASE
      WHEN role = 'recrutador' THEN 'rh'
      WHEN role = 'administrador' THEN 'administrador'
      ELSE role
    END INTO user_role
  FROM public.usuarios_rh
  WHERE user_id = (event->>'user_id')::uuid
    AND ativo = true
    AND deleted_at IS NULL;

  -- If not RH, check candidatos
  IF user_role IS NULL THEN
    PERFORM 1 FROM public.candidatos
    WHERE user_id = (event->>'user_id')::uuid;
    IF FOUND THEN
      user_role := 'candidato';
    END IF;
  END IF;

  claims := event->'claims';

  IF jsonb_typeof(claims->'app_metadata') IS NULL THEN
    claims := jsonb_set(claims, '{app_metadata}', '{}');
  END IF;

  -- Default to 'candidato' if no role found (new users during registration)
  claims := jsonb_set(claims, '{app_metadata, role}', to_jsonb(COALESCE(user_role, 'candidato')));

  event := jsonb_set(event, '{claims}', claims);
  RETURN event;
END;
$$;

-- Grant permissions for auth admin to execute the hook
GRANT EXECUTE ON FUNCTION public.custom_access_token_hook TO supabase_auth_admin;
REVOKE EXECUTE ON FUNCTION public.custom_access_token_hook FROM authenticated, anon, public;

-- Grant read access to the tables the hook queries
GRANT SELECT ON public.usuarios_rh TO supabase_auth_admin;
GRANT SELECT ON public.candidatos TO supabase_auth_admin;
```

Note: The hook maps `'recrutador'` from the DB to `'rh'` in the JWT for consistency with frontend route prefixes (`/rh/*`). This resolves Open Question 1 from RESEARCH.md.

**Migration 4: `supabase/migrations/20260420000003_check_candidato_duplicate_rpc.sql` (per D-01a, FOUND-10):**

Create the RPC function exactly as specified in RESEARCH.md Pattern 3:
```sql
-- Migration: RPC SECURITY DEFINER for duplicate check
-- Requirements: FOUND-10, D-01a
-- Replaces anonymous SELECT on candidatos with a function that returns only boolean flags.

CREATE OR REPLACE FUNCTION public.check_candidato_duplicate(
  p_cpf text,
  p_email text
)
RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  result jsonb;
BEGIN
  SELECT jsonb_build_object(
    'cpf_exists', EXISTS(SELECT 1 FROM public.candidatos WHERE cpf = p_cpf),
    'email_exists', EXISTS(SELECT 1 FROM public.candidatos WHERE email = p_email)
  ) INTO result;

  RETURN result;
END;
$$;

-- Only anon and authenticated can call this
GRANT EXECUTE ON FUNCTION public.check_candidato_duplicate TO anon, authenticated;
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> Postgres RPC | Anonymous users can call check_candidato_duplicate but only get boolean flags, not raw data |
| Auth pipeline -> JWT | Custom Access Token Hook injects role into JWT before it reaches the client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-09 | Information Disclosure | check_candidato_duplicate RPC | mitigate | SECURITY DEFINER with `SET search_path = ''`; returns only boolean flags, never raw candidato data |
| T-1-10 | Elevation of Privilege | custom_access_token_hook | mitigate | Function has GRANT only to supabase_auth_admin; REVOKE from authenticated/anon/public; cannot be called by regular users |
| T-1-11 | Denial of Service | check_candidato_duplicate RPC | accept | Anon can call repeatedly; rate limiting is at Supabase infrastructure level (API rate limits). Low risk for MVP. |
| T-1-12 | Information Disclosure | candidatos table anon SELECT | mitigate | Migration 0001 revokes any anonymous SELECT policy; only RPC exposes boolean flags |
</threat_model>
