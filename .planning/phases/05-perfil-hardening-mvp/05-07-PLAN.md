### GAP-05-CI-4 / GAP-05-CI-5 (a11y) — ROOT CAUSE CONFIRMED
The axe failures on /auth/login, /auth/redefinir-senha, /cadastro, /vagas are ALL `color-contrast` (serious), `fgColor #ffffff` on `bgColor #d9d9d9..#e5e5e5`, contrast ~1.25–1.41. The failing nodes are EVERY white-text element (h1 "Entrar", paragraphs, labels), not just buttons. The page genuinely renders white text over `BackgroundImage background="gradient"` (a `.jpeg` loaded via inline `background-image: url(...)` with `opacity-0` until onload). axe-core CANNOT evaluate contrast against a CSS background-image — it walks up to the nearest SOLID background color, finds `body { bg-background }` = `#ffffff` (globals.css:53,162-163), and reports white-on-light. This is the textbook axe background-image limitation, made deterministic-failing because the image is async/absent in CI.
- Tokens are NOT broken: D-07 channel-triplet repair landed in 05-02 (globals.css:46-70). Do NOT touch tokens.
- This is why 05-04 measured "zero violations" (dev session, image cached/loaded in time) but the live CI run failed (cold image load / scan-before-onload).
- The fix is at the shared primitive `BackgroundImage`: render a SOLID dark base color (`#00109E`, brand primary, ~12:1 vs white) as the bottom-most layer, immediately and unconditionally, BEHIND the image. This (a) is a real a11y/resilience improvement — white text always has a dark backdrop even if the image 404s — and (b) gives axe a solid dark ancestor to compute against, so contrast passes. All 4 failing public routes use BackgroundImage (LoginCandidatoPage:218, CadastroPage:37, VagasPublicasPage:169, RedefinirSenhaPage:184) → one edit cascades.
