## Scenario 3: FLOW-RECOVERY (AUTH-04) — Recovery deeplink → setNewPassword → /perfil

**Por que manual:** SC-3 Playwright já cobre via mocks de `/auth/v1/user`, mas isso não exercita o email round-trip + listener real. Este cenário valida que o caminho real-world (Gmail inbox → magic link click → /redefinir-senha → setNewPassword → SIGNED_IN listener → hydrateFromSession → navigate) funciona end-to-end.

**Passos:**

1. **Logout** se logado. DevTools → Application → Storage → "Clear site data".
2. Navegar para http://localhost:3003/auth/esqueci-senha.
3. Inserir `fernando@beautysmile.com.br`. Clicar "Enviar link de recuperação".
4. Esperado: toast verde anti-enumeração `Se este email estiver cadastrado, você receberá um link.`
5. **Abrir Gmail inbox** (do email do test user). Procurar email do Supabase (assunto típico: `Reset Your Password`).
6. **Clicar no link de recuperação** no email (deve abrir aba nova com URL `/auth/redefinir-senha#access_token=...&type=recovery`).
7. Preencher nova senha forte (ex: `NovaSenh@1234567`). Confirmar nova senha.
8. Clicar "Alterar senha".

**Esperado pós-submit:**
- Toast verde: `Senha alterada com sucesso.`
- Navegação aterrissa em `/candidato/perfil`.
- **`nome_completo` visível** (mesmo critério do Scenario 1).
- DevTools Console: zero red errors.

**Status:** [x] PASS / [ ] FAIL

**Evidence:**
- email recebido (`fernando@beautysmile.com.br`): `YES — fluxo perfeito, troca de senha completou + redirect para /candidato/perfil`
- nova senha aceita: `YES on retry — first attempt returned 422 from auth/v1/user (likely password-matches-current or weak-password rejection); retry succeeded`
- nome_completo visible on /perfil: `assumed YES (Fernando: "fluxo perfeito")`
- console errors: `1 transient (422 on first setNewPassword retry — recovered) + baseline DOM password-not-in-form ×3 (perfil change-password section, pre-existing)`
- timestamp: `2026-04-27`

**Side findings (cosmetic / UX — non-blocking):**
- **F-04.1-D (test setup, not a regression) — `paulista@beautysmile.com.br` recovery email did not arrive.** Verified user IS in auth.users (`userId: 95bc75ff-dc45-453e-b9e1-c92698714e06` from Scenario 1) with `email_confirmed_at` set (cadastrar-candidato EF uses `admin.createUser({ email_confirm: true })`). Email was sent by Supabase but destination mailbox does not receive — `paulista@beautysmile.com.br` is a placeholder used for cadastro testing without a real inbox in Beauty Smile's email server. **Recommendation:** future cadastro tests should use Gmail+alias addresses (e.g. `fernando+paulista@gmail.com`) so recovery emails route to a real inbox. NOT a Phase 4.1 regression — recovery flow itself works (proven via `fernando@`).
- **F-04.1-E — 422 transient on first setNewPassword.** `passwordService.ts:133 [AUTH] updateUser error` followed by retry success. Likely cause: Supabase Auth rejection ("password matches current" OR "weak password" OR token expired). UI did not surface a user-friendly error message before the retry — recommend mapping 422 to a clearer toast (e.g., "Esta senha não pode ser igual à atual" / "A senha não atende aos requisitos mínimos"). UX gap, not auth-hydration regression.

**Importante:** após este cenário, a senha mudou. Lembre de atualizar `.env.local` se você usa esse user em E2E (`TEST_USER_PASSWORD=...`) OU re-faça reset com a senha que você quer manter.
