# Phase 4.1: Auth Hydration Fix (INSERTED) — Research

**Researched:** 2026-04-26
**Domain:** Auth state hydration race + redirect-after-anon flow + JWT role fallback + Playwright smoke-runtime gate
**Confidence:** HIGH (root cause + fix verified via codebase grep + Supabase official docs via Context7)

## Summary

A única causa real dos 3 broken flows do `v1.0-MILESTONE-AUDIT.md` é uma divergência declarada na arquitetura do `authStore`: `initialize()` chama `fetchProfile()`, mas `setSession()` (linha 284 de `src/store/authStore.ts`) **não chama**. Como `App.tsx:152-186` invoca `initialize()` apenas no mount e despacha **somente** `setSession()` em todos os eventos `onAuthStateChange` (`SIGNED_IN`, `TOKEN_REFRESHED`, `USER_UPDATED`), qualquer login que aconteça **depois** do mount inicial deixa `profile` e `candidato` em `null`. O bug foi diagnosticado em Phase 1 carryover (`KNOWN-ISSUES-CARRYOVER-PHASE-3.md:81` "Opção B") e nunca implementado. Phase 4 UAT-J05 não exercitou o caminho `anon → /vagas → Candidatar-se → /auth/login → submit`, então a regressão atravessou todos os gates.

Existem 4 flows distintos que precisam hidratar `candidato` antes de navegar: (1) `tryAutoLogin` no Step 4 do cadastro, (2) `signIn` na `LoginCandidatoPage`, (3) `setNewPassword` na `RedefinirSenhaPage`, (4) `signIn` na `LoginCandidatoPage` quando vindo de `/auth/login?redirect=/candidato/candidatura/formulario/:slug`. Todos os 4 falham pelo mesmo motivo. O FormularioCandidaturaPage submit handler (`FormularioCandidaturaPage.tsx:233`) tem um early-return silencioso (`if (!cvFile || !user || !candidato || !vaga) return`) que torna o failure mode invisível ao usuário.

Existe também um **risco latente independente** (INT-WARNING-3): se o JWT Custom Access Token Hook parar de emitir `app_metadata.role`, `extractRole()` retorna `null` e o `RoleGuard` (linha 118) entra em loop de redirect infinito (login → setSession sem fallback DB → role=null → redirect /auth/login?redirect=/candidato/perfil → loop). `initialize()` tem fallback DB; `setSession()` não. Mesma classe de bug, mesma fix surface.

**Primary recommendation:** Substituir `setSession(session)` no listener `onAuthStateChange` por uma versão hidratante (chame ela `hydrateFromSession(session)` ou aliase para `initialize()`) que execute `fetchProfile` antes de marcar `isLoading=false`. O wrapping **deve** usar o pattern `setTimeout(async () => {...}, 0)` (oficial Supabase via Context7, ver §Common Pitfalls #2) para evitar deadlock no Web Locks. Esta única edição fecha INT-BLOCKER-1, INT-BLOCKER-2 e INT-WARNING-3 simultaneamente.

### Pattern 1: Hydrating onAuthStateChange listener (Supabase official, via Context7)

**What:** Defer Supabase async operations inside `onAuthStateChange` callback using `setTimeout(...,0)` to prevent Web Locks deadlock. Then call a hydrating action that does both `setSession` (fast) + `fetchProfile` (slow).

**When to use:** Always when the listener needs to make further Supabase calls (DB query, getUser, refreshSession). [CITED: https://supabase.com/docs/reference/javascript/initializing — fetched via Context7 `/websites/supabase`]

**Example (target Phase 4.1 shape):**

```ts
// App.tsx (Phase 4.1 target)
// Source: Supabase official pattern (Context7 /websites/supabase + GH issue 762)

const { data: { subscription } } = supabase.auth.onAuthStateChange(
  (event, session) => {
    // Sync work: update minimal session/user state immediately
    if (event === 'SIGNED_OUT') {
      clearAuth()
      return
    }

    // Async work (fetch profile) MUST be deferred to avoid deadlock
    setTimeout(async () => {
      if (event === 'SIGNED_IN' || event === 'TOKEN_REFRESHED' ||
          event === 'USER_UPDATED' || event === 'PASSWORD_RECOVERY') {
        // hydrateFromSession does setSession + fetchProfile + sets isLoading=false
        await useAuthStore.getState().hydrateFromSession(session)
      }
    }, 0)
  }
)
```

**Why setTimeout(0):** O callback de `onAuthStateChange` roda dentro do Web Lock interno do supabase-js. Qualquer `await` de outro método Supabase no mesmo tick pode deadlockar (a próxima chamada nunca retorna). `setTimeout(0)` defere a execução para o próximo event loop tick depois que o lock é liberado. [CITED: https://github.com/supabase/auth-js/issues/762]

### Pattern 2: Hydrate-before-navigate (defense in depth)

**What:** Submit handlers que navegam imediatamente após auth state change devem esperar o store reportar `candidato !== null` antes de chamar `navigate(...)`.

**When to use:** Em pages que (1) disparam um signIn/setNewPassword/tryAutoLogin e (2) navegam para uma rota que depende de `candidato` populado para renderizar corretamente (perfil, formulário de candidatura).

**Example:**

```ts
// LoginCandidatoPage.tsx (Phase 4.1 target — Pattern 2 layer)

const onSubmit = async (data: LoginFormData) => {
  setLastError(null)
  try {
    await signIn({ email, senha, rememberMe })

    // Defense in depth: even though listener (Pattern 1) hydrates, the submit
    // handler may complete BEFORE setTimeout(0) → fetchProfile resolves.
    // Block navigation until candidato is populated OR a hard timeout (e.g., 3s).
    await waitForCandidatoHydrated({ timeoutMs: 3000 })

    toast.success('Login realizado com sucesso!')
    const target = resolveRedirect(searchParams.get('redirect'))
    navigate(target, { replace: true })
  } catch (err) { /* ... */ }
}
```

```ts
// new helper — src/features/auth/utils/waitForCandidatoHydrated.ts

import { useAuthStore } from '@/store/authStore'

/**
 * Aguarda candidato (legacy alias for `profile` when role==='candidato') ser
 * populado no store. Usado por submit handlers que precisam navegar para uma
 * rota que depende de `candidato.id`.
 *
 * @param timeoutMs hard cap to avoid hanging forever (default 3000ms)
 * @returns true if candidato hydrated within window, false on timeout
 */
export async function waitForCandidatoHydrated(
  { timeoutMs = 3000 }: { timeoutMs?: number } = {}
): Promise<boolean> {
  const start = Date.now()
  while (Date.now() - start < timeoutMs) {
    const { candidato, role } = useAuthStore.getState()
    if (candidato && role === 'candidato') return true
    if (role && role !== 'candidato') return false  // RH/admin path; nav happens elsewhere
    await new Promise((r) => setTimeout(r, 50))
  }
  return false
}
```

### Pattern 3: JWT-role-null fallback in RoleGuard

**What:** Quando `isAuthenticated === true` e `currentRole === null`, evitar o redirect direto para `/auth/login` que cria loop (login bem-sucedido, role ainda null pela mesma razão). Em vez disso, disparar um one-shot `initialize()` (que tem fallback DB em `fetchProfile`) e re-checar.

**When to use:** Apenas no RoleGuard linha ~118. Defesa para INT-WARNING-3 (JWT hook misconfigured / dropped role claim).

**Example:**

```tsx
// RoleGuard.tsx (Phase 4.1 target snippet)

// 2. Não autenticado ou sem role → redireciona para login preservando destino
if (!isAuthenticated) {
  const redirectTo = encodeURIComponent(location.pathname + location.search)
  return <Navigate to={`/auth/login?redirect=${redirectTo}`} replace />
}

// 2b. Authenticated mas role===null: tenta um fallback DB antes de bouncar.
//     Previne INT-WARNING-3 redirect loop quando o JWT custom hook deixa de
//     emitir app_metadata.role.
if (currentRole === null) {
  // one-shot ref guard impede loop infinito de re-initialize
  if (!fallbackTriedRef.current) {
    fallbackTriedRef.current = true
    void useAuthStore.getState().initialize()
    return <LoadingDelay delay={200}><Loader2 className="..." /></LoadingDelay>
  }
  // fallback already tried; bounce to login as last resort
  const redirectTo = encodeURIComponent(location.pathname + location.search)
  return <Navigate to={`/auth/login?redirect=${redirectTo}`} replace />
}
```

### Anti-Patterns to Avoid

- **Async functions diretamente como callback de `onAuthStateChange`:** causa deadlock conhecido [CITED: https://github.com/supabase/auth-js/issues/762]. Use `(event, session) => { setTimeout(async () => {...}, 0) }`.
- **Chamar `await supabase.auth.getSession()` ou `supabase.from(...).select()` síncrono dentro do callback:** mesmo problema. Sempre defira.
- **Adicionar uma segunda subscription de `onAuthStateChange`:** Phase 1 já consolidou em UM único listener (App.tsx). Não regredir.
- **Bloquear `navigate(...)` indefinidamente esperando hidratação:** sempre incluir hard timeout (3s sugerido) com fallback "navigate anyway, page-level loading state cobre o resto".
- **Modificar `setSession` para fazer `await fetchProfile` síncrono no Zustand action:** Zustand actions devem ser rápidas/sync. Em vez disso: `setSession` (sync) + dispara fetchProfile como side-effect via `setTimeout(0)`.
- **Re-introduzir `setAdminUser` dual-role heurística para resolver hidratação RH:** o store unificado não precisa disso; `fetchProfile` resolve role corretamente via JWT + DB fallback.
- **Confiar que `initialize()` re-roda em `signOut` + `signIn` automaticamente:** ele NÃO roda — só no mount. O bug atual.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Polling do session em loop | Custom `setInterval(getSession, 1000)` | `supabase.auth.onAuthStateChange` (já wired) | SDK gerencia Web Lock, refresh, cross-tab storage events. Reinventar é frágil. |
| Decoder JWT customizado | `atob(token.split('.')[1])` à mão | `jwt-decode` (já instalado) | Edge cases de URL-safe base64 + erro silencioso para malformed |
| Próprio mecanismo de "wait for store update" | `setInterval` + busy-loop | Zustand `subscribeWithSelector` middleware OR o helper `waitForCandidatoHydrated` acima (50ms poll com hard timeout) | Zustand não tem `await store.dispatch().settle()` nativo; helper minimal é OK |
| Replicar `fetchProfile` em outro lugar | Inline query em `App.tsx` | Reutilizar `fetchProfile` privada do store ou expor como method | DRY + role fallback chain consolidado |
| Custom redirect-loop detector | Counter em sessionStorage + reset | `useRef` boolean dentro do RoleGuard (Pattern 3) | Componente já tem ref guard pattern (`toastFiredRef`); siga convenção |

## Common Pitfalls

### Pitfall 1: Silent return mascara erro post-redirect (the actual bug shipping today)

**What goes wrong:** `FormularioCandidaturaPage.tsx:233` faz `if (!cvFile || !user || !candidato || !vaga) return` — retorno silencioso sem toast, sem log. Após anon→login redirect, `candidato === null` por ~indefinidamente (até reload). User clica "Enviar candidatura", nada acontece, sem feedback. Phase 4 UAT NÃO viu porque a sessão da UAT-J05 já tinha `candidato` populado por `initialize()` no mount inicial.

**Why it happens:** `setSession` no listener não chama `fetchProfile`. Confirmed em `src/store/authStore.ts:284-294` (5 linhas, zero referência a `fetchProfile`).

**How to avoid:**
1. **Fix root cause:** hidratar no listener (Pattern 1).
2. **Defense in depth:** trocar o silent return por `toast.error('Sessão ainda carregando, aguarde...') + retry` ou bloquear o submit button com `disabled={!candidato}`.
3. **Smoke-runtime gate:** Playwright spec exercitando o caminho exato (anon → /vagas → /vagas/:slug → Candidatar → /auth/login?redirect=... → fill credentials → submit) que falharia se `candidato` ainda fosse null.

**Warning signs:** UAT manual com session pré-existente (sempre passa); UAT após `localStorage.clear()` em DevTools pode reproduzir.

### Pitfall 2: Deadlock no Web Lock por `await` síncrono dentro de `onAuthStateChange` callback

**What goes wrong:** Se Phase 4.1 implementar a fix ingenuamente — `onAuthStateChange(async (event, session) => { await fetchProfile(...) })` — o callback async re-entra no mesmo Web Lock que segura a operação atual. Próximas chamadas de Supabase (qualquer `from(...)`, `auth.getSession()`, `auth.refreshSession()`) hangam indefinidamente. Bug confirmado em produção em devices Chrome Android. [CITED: https://github.com/supabase/auth-js/issues/762, https://github.com/supabase/supabase-js/issues/2013]

**Why it happens:** supabase-js 2.x usa Web Locks API para serializar operações de auth. O callback de `onAuthStateChange` corre dentro do lock. Awaitar outra operação Supabase no mesmo tick = deadlock.

**How to avoid:** SEMPRE wrappar trabalho async em `setTimeout(async () => {...}, 0)` dentro do callback. Defere para o próximo event loop tick, depois do lock liberar. [CITED: Supabase official docs via Context7 — `https://supabase.com/docs/reference/javascript/initializing`]

**Warning signs:** Em desenvolvimento Chrome/Firefox desktop, o bug pode não aparecer (Web Lock libera rápido). Bug aparece em mobile real, em devices lentos, ou sob carga. Plan deve ter um teste isolado simulando isso (mockar timing? difícil — usar GH issue como reference + sempre aplicar o pattern).

### Pitfall 3: `PASSWORD_RECOVERY` event não é tratado em `App.tsx`

**What goes wrong:** O listener em `App.tsx:165-173` só checa `SIGNED_IN | TOKEN_REFRESHED | USER_UPDATED | SIGNED_OUT`. `PASSWORD_RECOVERY` cai no `else` (sem ação). Funciona hoje porque (a) `useRecoverySession` page-scoped escuta o evento separadamente, e (b) `setNewPassword` dispara `USER_UPDATED` depois, que então chama `setSession`. Mas isso é frágil: se Supabase mudar a ordem dos eventos, o flow quebra. Para Phase 4.1, com `setSession` agora hidratando, é trivial adicionar PASSWORD_RECOVERY ao mesmo branch.

**How to avoid:** Adicionar explicit case `PASSWORD_RECOVERY` ao switch no listener (já recomendado em Pattern 1 acima).

### Pitfall 4: `initialize()` re-rodando concorrentemente

**What goes wrong:** Se o RoleGuard fallback (Pattern 3) chama `initialize()` enquanto o listener também está chamando `setSession` (ou `hydrateFromSession`), duas concurrent fetchProfile podem racear. Última-fetch-wins, mas o estado intermediate pode ser inconsistente (e.g., role flip-flop).

**How to avoid:** Adicionar um `isLoading` guard em `initialize` (já existe — `set({ isLoading: true })` no início). RoleGuard só dispara fallback se `!isLoading` (já filtra) e `fallbackTriedRef.current === false` (one-shot). Plano deve testar overlap.

### Pitfall 5: `tryAutoLogin` retornando `true` antes do `onAuthStateChange` ter rodado o callback

**What goes wrong:** `tryAutoLogin` chama `signInWithPassword` e retorna `{ error: null }` imediatamente. O evento `SIGNED_IN` é emitido pelo SDK em um microtask seguinte (ou tick). O Step4 navigate handler (`CadastroMultiStepForm.tsx:439`) corre IMEDIATAMENTE após `tryAutoLogin` retornar — antes do listener processar setSession. Se o `navigate` resolver primeiro, `/candidato/perfil` renderiza com state pre-login (clearAuth still active).

**Why it happens:** SDK semantics — `signInWithPassword` resolve quando o token é gravado em storage; `onAuthStateChange` fires after.

**How to avoid:** Pattern 2 — `await waitForCandidatoHydrated()` antes de `navigate()`. Hard timeout 3s.

### Pitfall 6: RoleGuard `isLoading` true bouncing já-autenticado a `/auth/login`

**What goes wrong:** Phase 4 review WR-07 já tratou isso parcialmente (FormularioCandidaturaPage:146-153). Pattern: durante hydration race, `isLoading=true` por instantes; depois `isAuthenticated=false` por outro instante; depois `true`. Se um guard checa só `isAuthenticated`, ele pode bouncer um logged-in user erroneamente. RoleGuard atual usa `if (isLoading) return <Loader />` (linha 107) primeiro — está correto.

**How to avoid:** Não regredir o gate de `isLoading`. Plano deve assertir via E2E que após signIn não há flicker para /auth/login.

### Pitfall 7: Ordem do redirect query param em LoginCandidatoPage

**What goes wrong:** `resolveRedirect()` (LoginCandidatoPage:61) já tem anti-open-redirect guard; resolveu VAGA-03. Mas a hidratação fix não pode regredir esse comportamento. Quando o redirect é `/candidato/candidatura/formulario/:slug`, `RoleGuard role="candidato"` precisa de `role === 'candidato'` ANTES de a navegação aterrissar — se navigate dispara antes de hydration, o guard bouncea para login (loop).

**How to avoid:** Pattern 2 (await hydration) cobre. E2E spec deve covar o caminho com slug real.

## Open Questions

1. **Onde colocar `waitForCandidatoHydrated`?**
   - What we know: 3 call sites (LoginCandidatoPage, Step4 cadastro, RedefinirSenhaPage). Edge case: `VagaDetalhePage handleCandidatar` quando logged-in já não precisa (não dispara signIn).
   - What's unclear: É melhor uma utility em `src/features/auth/utils/`, OU um hook `useCandidatoHydrated()` que retorna boolean?
   - Recommendation: utility async function (Pattern 2 example). Hooks-as-promises são confusos; submit handlers já são async.

2. **`hydrateFromSession` deve ser uma nova action no store, ou `setSession` deve ser modificado?**
   - What we know: docstring atual de `setSession` (authStore.ts:88) diz só "session". Mudar comportamento dela é tecnicamente breaking change.
   - What's unclear: legacy callers (`setAdminSession`, alias) podem quebrar?
   - Recommendation: criar nova action `hydrateFromSession`. Manter `setSession` como sync-only (pega state mínimo do JWT). Faz o listener chamar `hydrateFromSession`. Reduz blast radius.

3. **Defense in depth no FormularioCandidaturaPage:233 — substituir silent return ou só remover?**
   - What we know: o silent return existe porque guard vem antes da chamada async; replace by `disabled={!candidato}` no botão é o caminho clean. Toast no submit handler também serve mas só se user clica.
   - What's unclear: planner deve decidir entre (a) `disabled` no botão (preventive UX), (b) toast no handler (reactive UX), ou (c) ambos.
   - Recommendation: ambos. `disabled` no botão + toast no handler como fail-safe.

4. **`PASSWORD_RECOVERY` event handling: explícito vs implícito via `USER_UPDATED`?**
   - What we know: hoje funciona via `USER_UPDATED` que vem depois de `setNewPassword`. Adicionar PASSWORD_RECOVERY ao switch é trivial.
   - What's unclear: SDK garante a ordem dos eventos? (PASSWORD_RECOVERY → user submits → USER_UPDATED) Ou pode haver outros casos?
   - Recommendation: adicionar PASSWORD_RECOVERY ao switch (defensivo). `useRecoverySession` page-scoped continua funcionando independente.

5. **Quanto smoke-runtime gate é "suficiente" para Phase 4.1?**
   - What we know: 1 Playwright spec novo cobrindo FLOW-CANDIDATURA fresh-login. ROADMAP success criterion #6 menciona explicitamente.
   - What's unclear: também cobrir FLOW-CADASTRO + FLOW-RECOVERY + FLOW-LOGIN-with-redirect? Combinatorial 4 flows × cenário fresh.
   - Recommendation: 1 spec com 4 cenários (test cases dentro do mesmo `describe`). Cada caso valida (a) flow completa, (b) `candidato` populated by Playwright `page.evaluate(() => localStorage.getItem('auth-storage'))` ou via UI assertion (e.g., `expect(page.getByText(NOME_DO_CANDIDATO)).toBeVisible()`). Test isolation via `beforeEach: clearCookies + localStorage.clear`.

6. **`useSessionTimeout.ts:19` — refactor para consumir `useAuthStore` diretamente, ou re-alias na página?**
   - What we know: o hook só lê `isAdminAuthenticated`. Trivial refactor.
   - What's unclear: se há outros pontos do hook que dependem de campos legacy.
   - Recommendation: refactor para `useAuthStore`. Manter lazy compat se planner achar necessário.

## Security Domain

> `security_enforcement` is enabled by default; this section covers the auth-state surface area.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | YES | Supabase Auth (JWT + custom hook); password redefinition via PKCE recovery deeplink (Phase 3 lock D-09 anti-enumeration) |
| V3 Session Management | YES | `persistSession: true` + `rememberMeStorage` adapter (Phase 3 D-19); session refresh via `autoRefreshToken: true`; PASSWORD_RECOVERY event-scoped session (Phase 3) |
| V4 Access Control | YES | RoleGuard centralizado (Phase 1 / Plan 01-03) + RLS policies (server-side authoritative). Phase 4.1 Pattern 3 fallback adds defense without weakening RLS. |
| V5 Input Validation | YES | Zod schemas (loginSchema, redefinirSenhaSchema, candidatoFormSchema); EF submit-candidatura Zod validates server-side. Phase 4.1 não adiciona inputs novos. |
| V6 Cryptography | NO | Não toca cripto. JWT decoding uses `jwt-decode` (decode only — verification feita pelo Supabase server). |

### Known Threat Patterns for Phase 4.1 stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Open redirect via `?redirect=` query param | Tampering | `resolveRedirect` anti-open-redirect guard (Phase 4 / Plan 04-07; 11 Vitest cases) — não regredir |
| Race-condition role escalation: anon→login redirect lands on candidato page with `role=null` momentarily, then admin URL injected | Elevation of Privilege | RoleGuard linha 107 gates on `isLoading`; Pattern 3 fallback NÃO escalates (DB query no-ops if user not in usuarios_rh nor candidatos — returns role='candidato' default per `fetchProfile` linha 200-202) |
| Deadlock in onAuthStateChange (Pitfall 2) — adversarial timing on mobile | Denial of Service | `setTimeout(...,0)` defer pattern (Supabase official). Plan deve ter assertion no listener para garantir o pattern. |
| Role JWT replay (stolen token) — `extractRole` decodes claim mas não verifica assinatura | Spoofing | Não é Phase 4.1 scope; mitigated by Supabase server (RLS valida JWT signature on every query). `extractRole` é apenas UX optimization client-side. |
| State leak across tabs (mismatched `role` em localStorage) — partialize do Zustand persist | Information Disclosure | `partialize` (authStore.ts:439-444) NÃO inclui `profile` nem `candidato` — só `user/session/role/isAuthenticated`. Após Phase 4.1, hidratação tem que rodar a cada tab abertura (initialize on mount já faz). Não regredir o `partialize`. |
| Session expired mid-flow (recovery PKCE) — `setNewPassword` falha com session_expired | Tampering | `RedefinirSenhaPage:84-99` Pitfall 2 fallback via `tryAutoLogin` (Phase 3 D-12). Phase 4.1 deve preservar — adicionar `await waitForCandidatoHydrated` DEPOIS do fallback signIn-by-password. |

### Threat Model Notes (specific to Phase 4.1)

- **Pattern 3 (RoleGuard fallback) NÃO bypassa RLS:** o fallback re-roda `initialize()` que faz query a `candidatos` / `usuarios_rh`. RLS já valida ownership. Pior caso: usuário sem profile cai em `role='candidato'` por default (linha 200-202 do `fetchProfile`) — mas RLS continua valendo nos selects subsequentes; user vê apenas suas próprias rows ou empty state.
- **Pattern 2 (`waitForCandidatoHydrated`) tem hard timeout 3s:** no pior caso, navega sem hidratação. RoleGuard ainda corre; se `role !== 'candidato'`, bouncea para home do role correto. Não há janela de privilégio elevado.
- **Pitfall 7 preservado:** zero `console.*` em candidato pages. `waitForCandidatoHydrated` utility também sem `console.*`. Asserted via grep guard (já existente, extend `PHASE_3_AUTH_PATHS`).
