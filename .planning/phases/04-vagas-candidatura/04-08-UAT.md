## UAT-J01: Upload real de PDF para bucket privado (CAND-01 / D-07 / T-04-12)

**Por que manual:** Storage real exige sessão autenticada + round-trip de rede;
flaky em CI headless.

**Passos:**

1. Abra https://app.beautysmile.com.br (ou http://localhost:3003) em uma sessão
   **normal de Chrome** (NÃO incognito — Phase 3 03-07 docfix carryover).
2. Faça login como candidato de teste (conta do Fernando).
3. Navegue para `/vagas` → clique em uma vaga ativa → clique em "Candidatar-se".
4. Na página do formulário, clique em "Selecionar arquivo PDF" → escolha um CV
   real (1-4 MB, PDF válido).
5. Verifique que o preview exibe: nome do arquivo + tamanho em MB/KB + botão "X"
   (remover).
6. Submeta o formulário.
7. Após o toast de sucesso + navegação para `/candidato/perfil`, abra Supabase
   Studio → Storage → bucket `curriculos` → confirme que existe um arquivo no
   path `<seu-auth-uid>/<uuid>.pdf` (D-10).

## UAT-J02: Perguntas reais → linhas em respostas_formulario persistidas (CAND-02 / CAND-03)

**Por que manual:** Verifica factory dinâmica de Zod + atomicidade da RPC
end-to-end com dados reais de perguntas.

**Passos:**

1. No Supabase Studio, garanta que a vaga escolhida tem 3+ perguntas configuradas
   (mistura de tipos: ao menos um `texto_curto`, um `single_choice`, um `numerico`).
2. Repita os passos 1-3 do UAT-J01 com essa vaga.
3. Preencha todas as perguntas obrigatórias com respostas realistas.
4. Submeta o formulário.
5. No Supabase Studio → Tables → `candidaturas` → confirme que existe uma nova
   linha com:
   - `status='aguardando_resposta'`
   - `etapa_atual='triagem'`
   - seu `candidato_id`
   - o `vaga_id` da vaga escolhida
   - `curriculo_url` não-nulo seguindo o schema do UAT-J01
6. Tables → `respostas_formulario` → confirme que existem 3+ linhas com o
   `candidatura_id` correspondente, uma por pergunta respondida.

## UAT-J03: Candidatura duplicada bloqueada server-side (CAND-04 / T-04-05 / DUPLICATE_APPLICATION)

**Por que manual:** Verifica UNIQUE partial index + mapeamento EF
DUPLICATE_CANDIDATURA → DUPLICATE_APPLICATION sob condições reais.

**Passos:**

1. Reuse o candidato + vaga do UAT-J01/J02.
2. Navegue novamente para `/vagas/<slug>` → clique em "Candidatar-se".
3. Resultado esperado (defesa em profundidade):
   - **Caminho A:** A página detecta candidatura existente via `useHasApplied` e
     mostra um toast "Você já se candidatou a esta vaga" + redireciona para
     `/vagas/<slug>` (não chega ao formulário).
   - **Caminho B:** Se `useHasApplied` está atrasado, a tentativa de submit
     dispara o EF que retorna `DUPLICATE_CANDIDATURA` → frontend mapeia para
     `DUPLICATE_APPLICATION` → toast "Você já se candidatou a esta vaga".
4. Confirme que **NENHUMA nova linha** foi criada na tabela `candidaturas`
   (consulte Supabase Studio).

## UAT-J04: Bucket é privado (T-04-12 — cross-check public bucket misconfiguration)

**Por que manual:** Confirma a configuração de RLS em nível de bucket sob
condições REST reais.

**Passos:**

1. A partir do UAT-J01, copie o path `<seu-auth-uid>/<uuid>.pdf` do CV uploaded.
2. Em uma aba **INCOGNITO** do navegador (sem sessão), tente um GET em:
   ```
   https://isljnozzlvckrgjjbjwp.supabase.co/storage/v1/object/public/curriculos/<seu-auth-uid>/<uuid>.pdf
   ```
3. **Esperado:** HTTP 400 ou 404 (bucket privado — nenhum path `/public/` resolve).
4. Verifique também na UI do Supabase Studio Storage que o bucket está marcado
   como **"Private"** com `file_size_limit = 5 MB` e
   `allowed_mime_types = [application/pdf]`.

## UAT-J05: Estabilidade do slug + roundtrip do redirect-pós-login (VAGA-02 / VAGA-03)

**Por que manual:** Verifica contrato de URL persistente + preservação do
`?redirect=` através do fluxo completo de autenticação.

**Passos:**

1. Faça logout (sessão anônima).
2. Navegue para `/vagas` → copie a URL com slug de uma vaga (e.g.
   `/vagas/atendimento-ao-paciente`).
3. Abra uma **nova aba**, cole essa URL → a página carrega com os detalhes da
   vaga (sem UUID; formato slug).
4. Clique em "Candidatar-se" → esperado: redirect para
   ```
   /auth/login?redirect=%2Fcandidato%2Fcandidatura%2Fformulario%2Fatendimento-ao-paciente
   ```
   (ou path semelhante URL-encoded).
5. Faça login.
6. Após o login, a página **DEVE** aterrissar em
   `/candidato/candidatura/formulario/atendimento-ao-paciente` — **NÃO** voltar
   para `/vagas/atendimento-ao-paciente`.

## UAT-J06: Redação no DevTools (Pitfall 7 / T-04-07 — production DevTools inspection)

**Por que manual:** Verifica que **nenhum signed URL token, nome de arquivo
PII, senha, ou access_token** vaza no console ou na network tab sob inspeção
real.

**Passos:**

1. Abra DevTools → torne visíveis as abas Console + Network.
2. Navegue para `/candidato/candidatura/formulario/<slug-de-vaga-real>` (logado).
3. Faça upload de CV (cv-sample-1mb.pdf ou um PDF real).
4. Submeta a candidatura (ou dispare qualquer toast).
5. **No Console:** percorra TODAS as entradas de log desde o carregamento da
   página. Verifique:
   - **NENHUM** `console.log` contém o nome literal do arquivo CV.
   - **NENHUMA** entrada contém uma string iniciando com
     `https://...storage/v1/object/sign/curriculos/` (signed URL).
   - **NENHUMA** entrada contém `?token=`, `access_token`, `refresh_token`,
     `senha`, `password`.
   - Entradas da camada de service ESTÃO presentes e usam shape redacted (e.g.,
     `{sizeKb, mime, hasFile}` para `cvUploadService`;
     `{vaga_id, candidato_id, respostas_count}` para `candidaturasService`).
6. **Na aba Network:** localize o POST para `/functions/v1/submit-candidatura` →
   confirme:
   - URL da request **sem** query params sensíveis.
   - Response body contém `{ok: true, data: {candidaturaId}}` (caso de sucesso)
     OU `{ok: false, error_code, message}` (caso de erro).
