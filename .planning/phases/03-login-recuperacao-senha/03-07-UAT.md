## UAT-1 (B6) — Lembrar-me CHECKED → session survives tab close

**Behavior ID:** B6 (AUTH-02 / D-05 / T-03-04)
**Why manual:** Playwright `context.close()` is not equivalent to a real tab
close for sessionStorage / localStorage semantics. Real browser only.

**Steps:**

1. Run `npm run dev` (Vite dev server on port 3003).
2. Open Chrome incognito → navigate to `http://localhost:3003/auth/login`.
3. Confirm "Lembrar-me" checkbox is **CHECKED** (D-05 default).
4. Sign in with a real test-seed candidato account (e.g. one of the seeded
   `test+*@beautysmile.com.br` users from Phase 2).
5. Land on `/candidato/perfil`.
6. DevTools → Application → Local Storage → confirm `sb-auth-token` exists.
7. DevTools → Application → Session Storage → confirm `sb-auth-token` does
   **NOT** exist (rememberMeStorage routed to localStorage).
8. Close the **entire** Chrome browser.
9. Reopen Chrome → navigate to `http://localhost:3003/candidato/perfil`.

**Expected:** Still authenticated, lands on `/candidato/perfil` directly
(no redirect to `/auth/login`).

- [x] **UAT-1 verified** by Fernando on 2026-04-25

**Anomalies / observations:**

The runbook step 2 instructed "Open Chrome incognito". This is **not the right
test environment** for this scenario. Chrome incognito wipes all storage when
the last incognito window closes — meaning even with Lembrar-me CHECKED and
the SDK correctly routing to localStorage, the storage gets cleared by the
browser, not by app behavior. The test always "fails" in incognito regardless
of app correctness.

Re-tested in **regular (non-incognito) Chrome window** following the same
flow:

- DevTools → Application → Local Storage: `sb-*-auth-token` present after
  login (with full JWT payload + refresh token) ✅
- DevTools → Application → Session Storage: empty ✅ (D-19 ORDER-LOCK confirmed:
  rememberMeStorage routed to localStorage on first SDK write)
- After full Chrome quit (Cmd+Q) + relaunch, navigated directly to
  `/candidato/perfil`: landed on the page WITHOUT redirect to /auth/login ✅

Recommend updating the runbook step 2 to "Open regular (non-incognito)
Chrome window" for accurate replication.

3. **UNCHECK** "Lembrar-me".

7. Open a new tab → navigate to `/candidato/perfil`.

**Expected:** Redirected to `/auth/login` (session dead — sessionStorage
cleared on tab close).

- [x] **UAT-2 verified** by Fernando on 2026-04-25

Logged in with Lembrar-me UNCHECKED → sessionStorage populated, localStorage
empty → closed the tab → reopened a new tab and navigated to
`/candidato/perfil` → redirected to `/auth/login` (session dead). Confirms
sessionStorage routing + per-tab lifetime semantics.

## UAT-3 (B10 real email) — End-to-end deeplink → reset → auto-login

**Behavior ID:** B10 (AUTH-03 / AUTH-04)
**Why manual:** Supabase SMTP rate-limits + real inbox required. Mocked
B10-lite covers the `useRecoverySession.status === 'valid'` branch in CI;
this UAT covers actual email deliverability + deeplink hash-fragment parsing
under a real Supabase recovery token.

**Steps:**

1. Use a real email address you control (preferably a `test+*@beautysmile.com.br`
   seed account so the row gets cleaned by Phase 2 conventions).
2. Open `/auth/esqueci-senha` → submit the email.
3. Verify the inbox receives a Supabase password-reset email within 60s.
4. Click the deeplink in the email.
5. Confirm landing on `/auth/redefinir-senha#access_token=...&type=recovery`
   (hash fragment present; URL allow-listed in Step 2 of T-03-09 Dashboard
   audit).
6. Form renders with both password fields (Nova senha + Confirmar nova senha).
7. Fill new password (min 8 chars + upper + lower + number) → submit.
8. Land on `/candidato/perfil` with toast `Senha alterada com sucesso.`

**Expected:** Email arrives < 60s; deeplink resolves to working form;
new password is accepted; redirect to `/candidato/perfil` happens immediately
(D-12 — no countdown).

- [x] **UAT-3 verified** by Fernando on 2026-04-25

**Anomalies / observations — IMPORTANT FINDING (PKCE flow / cross-browser):**

First attempt was made by submitting `/auth/esqueci-senha` from **Chrome
incognito** and clicking the email link, which opened in **regular Chrome**
(default browser). Result: page loaded with
`?error=access_denied&error_code=otp_expired&error_description=Email+link+is+invalid+or+has+expired`
and "Link inválido ou expirado" message — even though the Supabase Auth Logs
showed `action=login`, `provider=recovery`, `grant_type=pkce` SUCCESS for the
verify step.

Diagnosis (confirmed by Supabase Auth Logs `/v1/logs/auth-logs`):

1. ✅ `/recover` POST 200 → email sent
2. ✅ User click → `/verify` 303 → SUCCESS (token consumed, redirected with
   `?code=ABC`)
3. ❌ Client-side `exchangeCodeForSession(code)` failed → `code_verifier`
   not in regular Chrome's localStorage (it was stored in incognito's
   isolated storage when `/recover` was originally called)
4. The app surfaced the failure as a generic "Link inválido ou expirado"
   page, indistinguishable from a real expiry

Re-tested with **same regular Chrome window** for both `/esqueci-senha`
submission AND email click. Full success: form rendered with new password
fields, password update completed (`PUT /user` 200 in logs), redirected to
`/candidato/perfil` immediately, console emitted
`[AUTH] setNewPassword invoked {hasPassword: true}` (redaction idiom
confirmed — no plaintext password in console).

**Production-only finding for Phase 4 backlog (not blocking Phase 3):** PKCE
recovery flow requires the **same browser/storage context** between
`/esqueci-senha` submission and the email click. Cross-browser/device clicks
silently fail with a generic "Link inválido" — users will likely retry,
consume more email rate-limit budget, and/or assume the system is broken.

Suggested mitigations (any one is sufficient):

- (a) Switch the recovery flow to **OTP code** (user types a 6-digit code
  from email into the original tab) — eliminates browser-context dependency.
- (b) Detect missing `code_verifier` on `/auth/redefinir-senha` and surface
  a specific copy: *"Para concluir a redefinição, abra este link no mesmo
  navegador onde você solicitou a recuperação."* with a "Solicitar novo
  link" CTA.
- (c) Switch from PKCE to implicit flow for recovery only — works
  cross-browser but loses PKCE security benefit. Not recommended.

action button retries and succeeds once connectivity is restored.

## UAT-5 (B14 password NOT in network request body or console) — DevTools inspection

**Behavior ID:** B14 (AUTH-01..04 / T-03-03)
**Why manual:** Static grep + Vitest pitfall7.grep cover console-leak paths.
DevTools inspection covers the network surface + verifies the redaction
discipline holds in actual runtime call frames.

**Steps:**

1. DevTools → Network tab, **Preserve log** ON.
2. Sign in with valid credentials.
3. Find `POST /auth/v1/token?grant_type=password`.
4. Inspect Request **Body** (Payload tab):
   - Expected: `{"email":"...","password":"..."}` — password IS in the body
     over HTTPS (Supabase needs it; this is correct).
5. Inspect Request **URL** (Headers tab):
   - Expected: password does **NOT** appear in the query string.
6. Switch to DevTools Console:
   - Find `[AUTH] signIn invoked` log.
   - Expected payload shape: `{ email, rememberMe, hasPassword: true }`.
   - **Forbidden:** any `{ password: 'plaintext' }`, `{ senha: '...' }`,
     or `password` appearing as a value (only `hasPassword: Boolean(...)` is
     allowed — the redaction idiom from Plan 03-04).
7. Trigger an invalid-credentials submit too (same flow with wrong password).
   - Inspect Console — `[AUTH] signIn error:` log should emit only
     `{ code, status }`. **Forbidden:** the error message containing `senha`
     / `password` plaintext.

**Expected:** Password is in the HTTPS body (correct) but never in URL,
query string, or console output. Console payload uses `hasPassword: true`
sentinel (per Phase 3 Pitfall 7 redaction idiom).

- [x] **UAT-5 verified** by Fernando on 2026-04-25

**Evidence captured (DevTools Network + Console):**

| Surface | Observation | Verdict |
|---------|-------------|---------|
| Request URL | `https://isljnozzlvckrgjjbjwp.supabase.co/auth/v1/token?grant_type=password` | ✅ Password NOT in URL/query string |
| Request Body | `{email, password: "<plaintext>", gotrue_meta_security: {}}` | ✅ Password in HTTPS body (correct — Supabase requires it) |
| Console (valid login) | `authService.ts:65 [AUTH] signIn invoked {email, rememberMe: true, hasPassword: true}` | ✅ Boolean sentinel, no plaintext |
| Console (invalid login error) | `authService.ts:84 [AUTH] signIn error: {code: 'invalid_credentials', status: 400}` | ✅ Only code+status, no plaintext password (neither correct nor wrong attempt) |

Phase 3 Pitfall 7 redaction idiom holds at runtime. The pitfall7.grep
Vitest test (committed at 6bcda7c) catches static regressions; this UAT
confirms the runtime contract.

**Anomaly (not a bug — environmental):** Chrome's password manager
auto-fills the "Digite sua senha atual" input on `/candidato/perfil` after
a successful login if the user has a saved credential for the site. The
DOM warnings about "Password field is not contained in a form" appear
because the change-password widget on the profile page uses bare inputs
without a `<form>` wrapper. **Not in scope for Phase 3** but flagged for
Phase 5 (profile / a11y improvements): wrap the change-password inputs in
a `<form>` element with proper autocomplete tokens
(`autocomplete="current-password"` / `"new-password"`) so the browser
hint is more deterministic.

## Findings summary (Phase 4 backlog candidates)

Three documented anomalies — none block Phase 3 closure, all flagged for
the next milestone:

1. **Runbook fix (process):** UAT-1 step 2 should say "regular Chrome
   window", not "Chrome incognito". Incognito wipes localStorage on full
   close, making the test scenario impossible to validate. Update needed
   in this runbook for future re-runs.

2. **PKCE cross-browser recovery (UX/product, Phase 4):** Password reset
   currently requires the user to click the email link in the **same
   browser/storage** where they submitted `/auth/esqueci-senha`. Cross-
   browser/device clicks fail silently with "Link inválido ou expirado"
   even when the Supabase verify step succeeded. See UAT-3 anomalies for
   three suggested mitigations (preferred: switch to OTP code).

3. **Profile change-password a11y (Phase 5):** The change-password
   widget on `/candidato/perfil` uses bare inputs (no `<form>` wrapper),
   which triggers Chrome DOM warnings and reduces password-manager
   determinism. Wrap inputs in `<form>` with explicit `autocomplete`
   tokens (`current-password` / `new-password`).
